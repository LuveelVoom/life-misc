rulesearch speedup ideas
========================

Measured baseline (rule A, 2000 soups, 1 thread, Linux, this sandbox):
  ~9.7 ns per cell-update overall; the sweep itself is ~2.3 ns (measured with scans disabled).
  => ~75% of time is the every-8-gens cluster scan + classification, not simulation.
  Note: simply disabling scans is SLOWER (ships never removed, soups never stabilise).
Gains below are estimates unless marked measured.

1. Reuse classifications across mutants   [identical results]
   Cache is cleared every evaluation, so every still life / blinker is re-simulated for each rule.
   A cluster's isolated evolution depends only on the transition classes it touches.
   Store (key -> Info, touched classes + their values); on lookup in a new rule, reuse if those
   classes are unchanged. Mutants differ in 1-3 classes, so most entries stay valid.
   Likely the biggest single win.

2. Cheaper scans
   a) [identical] No std::string keys / vector allocations in the hot path: 64-bit hash of the
      cluster bitmap, reusable buffers, flat open-addressing table.
   b) [identical] Skip scan when nothing changed since the last scan (hash equal and no ship
      candidates last time).
   c) [CHANGES COUNTS slightly - make it an option] only examine clusters within a few cells of the
      global bbox edge (escaping ships are on the frontier); adaptive scan interval (8 -> 16/32
      while no ship candidates are present).

3. Sweep: skip inactive tiles   [identical]
   Track 8x8 (or 16x16) tiles whose cells or neighbouring tiles changed last generation; only
   recompute those. Settled debris dominates late soup life. Est. 3-5x on the sweep.

4. Sweep: SIMD / bit-sliced rule evaluation   [identical]
   Per rule, build a BDD (or mux tree with shared nodes) of the 512-entry table; evaluate on 64
   cells per word (AVX2: 256) from the 9 shifted neighbour bitplanes. Typical rules have small
   BDDs, so ~5-10 ops/cell -> well under 1 ns/cell. Combine with 3.
   Cheaper variant: 2x2-cell lookup (16-bit index -> 4 output bits, 64 KB table), 4x fewer lookups.

5. Search level
   - Cache evaluations by rule-table hash (LAHC/explore revisit rules).   [identical]
   - Racing already drops ~60% of mutants early (measured). The 32-soup probe + per-soup
     cost limit gave ~5x per-iteration speedup (measured: ~6 s -> ~1 s/iter).
   - Adaptive N: stop the full evaluation early when the mutant is clearly better, not only worse.
   - Smaller grid (128) when soups stay small; grow only if a pattern reaches the border.
   - Reduce gmax once a rule's stabilisation time is known (e.g. 4x the 99th percentile).

6. Memory / setup   [identical, small]
   - Clear only the previously used bbox of the grids instead of 2 x 256x256 memset per soup.

7. Parallelism
   - Soups are independent; threads already scale. For many cores, run several climbs/explores
     on separate rule populations (island model) rather than larger soup batches.

Verification rule for any of these: same config + seed must reproduce identical census counts
single-threaded (the old engine is the oracle), except items marked CHANGES COUNTS, which need
a statistical comparison on fresh seeds instead.

=====================================================================
RESULTS (2026-10-22, Apple M4 Pro, g++-16, rule of examples/diag_ship_explore.cfg)
=====================================================================
Baseline on this machine: census 2000 soups 2.45 s single thread; profile: ~85% in classify()
(std::set inserts + stepCells allocations), ~15% in the sweep.

Implemented (all bit-identical to the old engine: census, climb 60 its at 1 and 7 threads, explore 50 its):
  A. classify on a local byte grid + exact cycle early-out (state repeats without c0 => c0 never recurs).
     census 2.45 -> 1.17 s
  B. Skip classification in non-final scans when all 8 directions of travel fail the escape-cone test
     (only ships matter before the final scan, and a blocked ship is discarded anyway).  1.17 -> 0.78 s
  C. NEON 16-cell sweep (64-byte bit table, tbl + per-lane shift) for soup and classification sweeps,
     incl. letting the last chunk overrun the region edge (those lanes are provably 0).  0.78 -> 0.42 s
  D. Lazy transition usage: counted only for rules actually mutated from (64 soups re-run with counting).
     Before, the slow counting sweep ran on the first 64 soups of EVERY evaluation = the whole climb probe.
  climb 60 its: 167 s -> 21 s (1 thread); 34 s -> 3.4 s (14 threads).

Tried and rejected (measured):
  1. Reuse classifications across mutants: a warm cache from another census of the same rule gives 0%
     (misses are unique chaotic clusters; repeated objects are already hits within one evaluation).
  -  Whole-soup reuse between parent and mutant (soup result depends only on table entries it used):
     0% of soups reusable - every soup uses essentially every class that fires at all.
  -  Prefix reuse (resume a mutant soup from the generation of first divergence): divergence happens at
     ~0.7% of soup lifetime on average (usage-weighted over mutation probabilities). Not worth it.
  -  Cache-ahead: after classifying a cluster, pre-fill the cache with the (provable) results for its states at
     +8, +16, ... gens. No gain: clusters almost never reappear unchanged 8 gens later (they interact/split).
  2c (frontier-only scans) not done: changes counts. 3 (inactive tiles): with B+C the sweep is ~25% of time.
  -  Skipping runs of 8 empty neighbourhoods in the scalar sweep: no gain (superseded by NEON).
Remaining profile: classification of chaotic clusters (~45%), scan clustering/escape test (~25%), sweep (~25%).
